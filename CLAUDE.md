# CLAUDE.md

Rails for this repo. Read this first, every session.

## What this is

A daily factory-automation puzzle. Small bounded grid, conveyor belts, a few machines. The player routes items from sources through transformations into a sink, scored against par like golf. Puzzles are generated by a model and filtered by an automated validator.

**Web first (Expo web), Android later from the same codebase.** iOS is deliberately out of scope.

## Read before touching simulation code

`docs/rules-spec.md` is authoritative for all simulation semantics. If code and spec disagree, **the spec wins** — fix the code, or change the spec deliberately and update the tests in the same commit.

§6 (tick order) and §7 (belt path resolution) are the parts that look arbitrary and are not. Downstream-first resolution is what makes a line of items advance together rather than one cell per tick. Do not "simplify" it.

## Architecture rules

**The simulator is a standalone package with zero rendering imports.** No React, no Expo, no DOM, no canvas. It is a pure function:

```ts
simulate(level: Level, solution: Solution): SimResult
```

This is non-negotiable and it is not architectural purism. The same function is the game engine *and* the Phase 3 puzzle validator. The moment it imports from the UI, headless batch validation becomes impossible and Phase 3 dies.

- `packages/sim/` — pure logic, no dependencies beyond the standard library
- `app/` — Expo app, imports `sim`, never the reverse
- No randomness anywhere in `sim`. If something needs to vary, it comes in through the level file.

## Rendering

Plain React Native `View` components. A 7×7 grid is 49 elements — no Skia, no canvas, no game engine. Easier to debug, easier to make accessible, and the animation needs are trivial.

## Workflow rules

- **Tests before UI.** All twelve test cases in §14 of the spec must pass before any rendering work begins.
- **Run the full suite before saying anything works.** Not a subset. Not "this should work."
- **The conservation invariant** (§14, case 10) stays asserted in debug builds permanently. It catches most movement bugs on the tick they happen rather than three features later.
- **Never change tick order without updating the affected tests in the same commit.** If a test needs changing to accommodate a code change, stop and flag it — that usually means the code is wrong, not the test.
- Small commits. One behaviour per commit.

## Stack

- TypeScript, strict mode
- Expo (React Native, web target)
- Vitest
- No state management library. Component state and a plain reducer are enough.

Do not add dependencies without asking. This project should stay boring.

## Current phase

**Phase 4 — the daily loop. Rotation, streaks, sharing.**

In scope: picking one puzzle per day from a committed pool, remembering what the player has done, and letting them share a result. `app/` work, no new packages.

Explicitly **not** in scope, do not build these even if they seem quick:

- Store assets, analytics, accounts (Phase 5)
- A backend of any kind. There is no server and there is not going to be one — the daily puzzle is a pure function of the date, and history lives in the browser.

**Phase 3 is done and its numbers are published.** `docs/writeup.md` cites the 50-candidate batch from seed 1, so `artifacts/` and the four acceptance criteria are now load-bearing for a document that exists in the world. Changing a §8 criterion re-scores that batch and invalidates the write-up; if a daily-loop need seems to require it, the answer is almost always to curate at the Phase 4 layer instead. **The validator decides whether a puzzle is valid; the daily loop decides whether it is a good Tuesday.** Those are different questions and they get different code.

**Animation is in scope** (reopened deliberately: the board read as dead, items teleported between ticks). It is **presentation only**. The simulator stays discrete and authoritative; the renderer interpolates between two consecutive snapshots. Never animate a guess, never let a tween decide anything the engine did not — what you watch must remain exactly what got scored.

**Phases 1 and 2 are done.** `packages/sim/` passes all twelve §14 cases plus a `spec-invariants` suite, verified falsifiable by mutation testing. Treat it as settled: if generation wants a behaviour change, that is a spec change first (§15, then tests, then code) — not an edit to the simulator to make a search terminate.

The validator **is** `simulate`. That is why the simulator has no rendering imports and no randomness — headless batch validation is the whole reason for that rule. If you find yourself wanting to import anything from `app/` into a validator, stop.

The UI drives the sim through the §13 stepping API — `createWorld`, `step`, `snapshot` — not by calling `simulate` and animating a guess. `snapshot` is the render input.

Level content lives in `levels/`. `levels/001.json` is the hand-designed fixture and the basis for most tests — see `docs/level-001.md` for why it's shaped the way it is. `levels/daily.json` is the rotation pool, generated rather than written; rebuild it with `scratchpad/build-daily-pool.ts` rather than editing it by hand.

**Which puzzle a date maps to is a pure function and must stay one.** No clock reads inside it, no `Date.now()` buried in a helper — the date comes in as an argument so the mapping can be tested at any point in the rotation, including the day the pool wraps. Same rule as the simulator, same reason.

## Things that have already gone wrong once

Kept as a running list. Add to it.

- Conveyors are `{in, out}` pairs, **not** rotations. Rotation-only belts can't turn corners, which makes every puzzle a straight line.
- `cost` is the **sum of building costs** from §4, not a count of buildings.
- Splitter and merger round-robin flags are simulation state. They must reset on run-reset and serialise with saved state. This is the most common source of non-determinism in this genre.
- A green suite is not a correct suite. Several §14 tests originally passed against a simulator with the round-robin flag disabled, because they asserted on item counts rather than observing the mechanic. When a test can't fail, it isn't testing. Mutation-check anything load-bearing: `scratchpad/mutate.ps1` is the pattern.
- On Windows, `Get-Content`/`Set-Content` round-trips corrupt every `§` and `—` in source files. Scripts that rewrite files must use `[System.IO.File]::ReadAllText`/`WriteAllText` with UTF-8. Tests do not catch this — comments don't run. `Get-Content` also *misrenders* correct files as mojibake on read, so check with the .NET API before "fixing" anything.
- A validator can understate as well as overstate. Five candidates were reported as `no_solution_found` — a bounded claim — when they were provably impossible on port counts. Stage A closes over item *types* and cannot see that `x + x -> y` needs two `x` at once, so a splitter-less level passed it and then burned a full search saying nothing. Erring toward the weaker claim is the safe direction, and it is still a bug.
- The planner has **no merger node, deliberately** — do not "fix" it. A merger adds a building and removes none, so it only pays through throughput, and throughput never binds at 5 items / 300 ticks. Measured: a winning merger layout costs 8 against 3 and is a tick slower. Planning them would add only dominated plans and inflate `distinctForms` with factories nobody would build. `merger` in a level's `available` therefore changes no verdict; a test asserts that. The one case outside the argument is merging two *different* item types onto a shared belt to save conveyors, which the one-item-per-node plan model cannot express — so the claim is bounded to plans the planner can represent, not to all solutions.
- An acceptance criterion can quietly select for **one shape of level** and look like it is working. Criterion 4 wants two materially different solutions; the generator emitted one assembler recipe, so the only structure that could ever satisfy it was an `x + x` pair with a splitter — and 30 of 31 accepted levels turned out to be that same puzzle with the item names changed. Measure the *distribution* of accepted shapes, not just the count. §2 had permitted the second recipe all along.
- When raising acceptance, check what it costs the **rejection log**. A press straight to the target scored 53/200 against 36, and got rejected: it gives the target a fan-out-free route, so `insufficient_fanout` fell 24 → 6 and one of only two proven codes was hollowed out to flatter a headline number. `scratchpad/mutate.ps1` carries a mutation that swaps the good design back to the bad one.
- The `tally` records the stage an attempt was **abandoned** at, which is not the stage that **caused** the failure. "94.8% die at routing" reads as a weak router; a rip-up-and-reroute measured over 200 candidates moved routing failures by 0.7% and acceptance not at all, which proves those failures are bad *placements* surfacing late. Do not optimise a stage because the tally column is large — confirm the cause first, or you will improve the wrong half of the pipeline.
- A weak search does not only lose candidates, it silently mis-scores the ones it keeps. `par` is the cheapest solution *found*, so every gap in the search ships as a puzzle scored too generously — improving the router dropped an accepted level's par from 26 to 21. No test catches this, because "cheapest found" is exactly what it claims to be. Re-run the batch after any search change; par is a function of how hard you looked.
- A search change that alters the *number* of restarts needs a **budget control** — the same restart count with the new heuristic off. Sampling roomier placements looked like it took acceptance 23 → 31, but it also doubled the budget; the control (500 restarts, heuristic off) scored 20, so the real effect was 20 → 31 and the naive reading credited the heuristic with twice the search. That control also moved acceptance *down* versus 250 restarts, which is how noisy the metric is.
- Acceptance and **par honesty are different axes and can move in opposite directions**. Preferring roomy cells spreads machines out, spread machines need longer belts, and the search stops finding the cheap compact layouts — it bought acceptance while making par looser on 39 levels against 14 tighter. The fix was to alternate tight and roomy restarts and *add* the roomy ones rather than reallocate. Always measure par excess alongside acceptance.
- Search tuning must be measured across **multiple seed ranges, paired**, never on the single canonical batch. Acceptance moves by two or three, and changing any search parameter reshuffles the whole PRNG stream, so an arm can look better for nothing. `scratchpad/confirm-route-retries.ts` is the pattern: same comparison over 200 candidates in four independent ranges.
- Any check whose verdict is reported as **proven** must not carry a search bound. The first draft of the fan-out check reused the planner's `maxDepth`, which would have turned "didn't look far enough" into "impossible" — precisely the conflation the rejection codes exist to prevent. If a bound is needed for termination it has to be one that provably cannot hide a positive (refusing to revisit a type on the current chain is such a bound; a depth limit is not).
